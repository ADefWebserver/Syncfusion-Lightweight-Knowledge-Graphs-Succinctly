Features to document:

Extend the existing Graph Chat assistant with a carefully controlled mutation path.
At this stage, the application already has a file-based graph under App_Data/graph, a
GraphStore that keeps it in memory, and a read-only /graphchat page that uses
Microsoft.Extensions.AI tools for deterministic queries. The assistant may now
propose changes, but no proposal should be applied until a person has reviewed a
preview and explicitly approved it. Every applied change must also be auditable.

There are two kinds of change, and they differ in where the truth lives.

The first kind edits a help-desk ticket. The SQL database remains the system of
record for tickets, so this change is written to SQL first and only then mirrored
into the graph. Exactly two ticket fields may be changed: status and description.
Nothing else about a Ticket, and no other database-derived node, may be edited.
TicketDetail, Requester, Status, and Day nodes stay strictly read-only, and no node
of any database-derived type may be created or deleted.

The second kind edits an optional graph-native knowledge layer that has no database
behind it at all: KnowledgeArticle and Resolution nodes, plus LINKED_TO edges from
Ticket to Ticket, REFERENCES_ARTICLE edges from Ticket to KnowledgeArticle, and
RESOLVED_BY edges from Ticket to Resolution. These live only in graph.json.

Use the same two-phase contract for every mutation:
MutationResult Name(args, bool confirmed = false). With confirmed set to false, the
operation must not write anything, to SQL or to disk. It should return a
MutationResult whose Preview contains a plain-language summary, the files that would
be affected, and any validation warnings. With confirmed set to true, the operation
applies the change, rebuilds the graph indexes, updates the manifest, appends an audit
entry, and returns the resulting state.

Put the shared mutation models in Services/Graph/MutationModels.cs, and make them
immutable records rather than mutable classes, so a preview cannot be altered between
the moment it is shown to a person and the moment the change is applied:

- MutationStatus is an enum with Rejected, PreviewOnly, and Applied.
- MutationPreview is a record with Summary, IReadOnlyList<string> AffectedFiles, and
   IReadOnlyList<string> Warnings.
- MutationResult is a record with Status, MutationPreview? Preview, and
   IReadOnlyList<string> Errors, plus static factory helpers named Rejected,
   PreviewOnly, and Applied.

Make Services/Graph/GraphMutationService.cs the only component allowed to write graph
files. Give it a private AuditFileName constant and a private PreviewFiles array
holding graph.json, manifest.json, and audit.log, so every preview reports the same
file list. Protect the write path with a static SemaphoreSlim so concurrent mutations
cannot interleave even though the service is registered as scoped. Keep a
ReadOnlyNodeTypes set containing Ticket, TicketDetail, Requester, Status, and Day, and
a separate EditableTicketProperties set containing status and description. Inject
GraphStore, IOptions<GraphOptions>, IWebHostEnvironment, and
IDbContextFactory<SyncfusionHelpDeskContext>.

Structure every mutation the same way, because the ordering is the safety model:

- Put all of the validation rules in a local function, MutationResult? Validate
   (GraphDocument doc), that returns null when the request is acceptable and a
   rejection otherwise.
- Load the document from disk, call Validate, and return early on rejection. Do not
   take the lock for this: a preview only reads, so previews never contend.
- Build the MutationPreview and return MutationResult.PreviewOnly when confirmed is
   false. Nothing has been written at this point, to SQL or to disk.
- When confirmed is true, take the lock, re-load the document from disk, and call
   Validate a second time. This matters: minutes can pass between a preview appearing
   on screen and a person clicking Approve, and the ticket may have been closed in the
   help-desk UI in the meantime. Re-validating under the lock means an approval can
   only ever apply to a state that still holds.
- Apply the change, then call a private CommitAsync helper.
- Release the lock in a finally block.

Always work on a GraphDocument freshly loaded from disk rather than the one held in
GraphStore, so a rejected or preview-only call can never leave the in-memory graph
half-changed.

CommitAsync is the shared tail of every applied mutation. It writes graph.json
atomically, writes manifest.json with the new lastMutationUtc, calls
GraphStore.ReloadAsync, and appends one tab-separated line to audit.log containing the
UTC timestamp in round-trip format and a detail string such as
"UpdateTicket id=ticket:42 property=status".

Specify UpdateTicket(ticketId, propertyName, value, confirmed) in detail, because it
is the only mutation that leaves the graph files. Its Validate function should check,
in order: the node exists; its Type is Ticket; propertyName is in
EditableTicketProperties; when the property is status, the value matches an entry in
HelpDeskStatusData.Statuses compared case-insensitively, and the rejection message
lists the valid ones; when the property is description, the value is not blank; and
the node id parses as ticket:<number> so the database key can be recovered.

Have the status check capture the canonical ID from the matching HelpDeskStatusData
entry rather than trusting the string the model sent, and write that canonical value.
A model that asks for "closed" should result in "Closed" in the database, so the
graph's status: ids stay consistent with the ones a full rebuild would produce.

Once confirmed, load the HelpDeskTicket by the recovered key, set TicketStatus or
TicketDescription, and call SaveChangesAsync. If the row has since disappeared, reject.
Then mirror the change into the graph in place. Do not rebuild the graph from the
database to pick up the edit: a full rebuild would discard the whole knowledge layer,
because articles, resolutions, and links exist only in graph.json. For a description
change, set the node label to the first 60 characters of the new text, matching the
builder's rule. For a status change, set the node's status data value and then repoint
its HAS_STATUS edge with a private RepointStatusEdge helper that creates the target
Status node if no ticket currently has that status, removes any existing HAS_STATUS
edge leaving the ticket, and adds the new one. Note in the plan that repointing can
leave an orphaned Status node behind when the last ticket moves off a status, and that
the next full rebuild removes it.

Also implement, following the same shape: UpdateNodeContent(nodeId, propertyName,
value) which sets one Data property or the label of an editable node and rejects any
type in ReadOnlyNodeTypes; LinkTickets(fromTicketId, toTicketId) which adds a
LINKED_TO edge and rejects self-links and duplicates in either direction;
AddKnowledgeArticle(title, content) which creates a KnowledgeArticle node with the id
article:<guid>; ReferenceArticle(ticketId, articleId) which adds a REFERENCES_ARTICLE
edge and rejects duplicates; RecordResolution(ticketId, content) which creates a
Resolution node with the id resolution:<guid> plus its RESOLVED_BY edge; and
DeleteArticle(articleId, cascade) which removes an article and its incoming edges but
is rejected while REFERENCES_ARTICLE edges still point at it unless cascade is true,
and which reports the number of edges it will remove as a preview warning. Every new
edge requires existing endpoints of the expected types.

Expose exactly two write tools to the AI model. Define IGraphWriteTools and
GraphWriteTools in Services/AI/GraphTools, with UpdateNodeContent(nodeId,
propertyName, value) for the knowledge layer and UpdateTicket(ticketId, propertyName,
value) for tickets. Both must return Task<MutationResult> rather than a formatted
string, so the model receives the status and any error messages as structured data
that cannot drift out of sync with the service. The service supports the full mutation
domain, but the model never sees LinkTickets, AddKnowledgeArticle, ReferenceArticle,
RecordResolution, or DeleteArticle: it cannot create or delete nodes, and it cannot
add, change, or remove an edge.

The [Description] on each tool must say what it can change, name the valid statuses
for UpdateTicket, state that UpdateTicket writes to the SQL database and mirrors into
the graph, state that database-derived nodes are otherwise read-only, and say that
calling the tool only produces a preview a human must approve.

Enforce the approval boundary in the class rather than in the prompt. Both
model-invoked methods must hard-code confirmed: false, and must stash the result as a
pending proposal only when the returned status is PreviewOnly, so a rejected request

List acceptance criteria. A preview call with confirmed == false writes nothing to
disk and nothing to SQL. Asking the assistant to change a ticket produces an approval
dialog, which proves the write tools were actually registered with the model. No
change is applied until the human clicks Approve. Rejecting, or closing the dialog,

one line to audit.log.
