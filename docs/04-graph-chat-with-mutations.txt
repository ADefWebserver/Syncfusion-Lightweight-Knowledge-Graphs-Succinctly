Features to document:

Extend the existing Graph Chat assistant with a carefully controlled mutation path.
At this stage, the application already has a file-based graph under App_Data/graph, a
GraphStore that keeps it in memory, and a read-only /graphchat page that uses
Microsoft.Extensions.AI tools for deterministic queries. The assistant may now
propose changes, but no proposal should be applied until a person has reviewed a
preview and explicitly approved it. Every applied change must also be auditable.

Keep all facts derived from the database read-only. Ticket, TicketDetail, Requester,
Status, and Day nodes cannot be created, changed, or deleted through this feature.
Instead, introduce an optional graph-native knowledge layer with KnowledgeArticle and
Resolution nodes. This layer may also contain LINKED_TO edges from Ticket to Ticket,
REFERENCES_ARTICLE edges from Ticket to KnowledgeArticle, and RESOLVED_BY edges from
Ticket to Resolution. Only graph-native nodes and edges may be managed by mutations.

Use the same two-phase contract for every mutation:
MutationResult Name(args, bool confirmed = false). With confirmed set to false, the
operation must not write anything. It should return a MutationResult whose Preview
contains a plain-language summary, the files that would be affected, and any
validation warnings. With confirmed set to true, the operation applies the change,
rebuilds the graph indexes, updates the manifest, appends an audit entry, and returns
the resulting state.

Document the supported operations and their validation rules. LinkTickets adds a
LINKED_TO edge but rejects self-links and duplicates in either direction.
AddKnowledgeArticle creates a KnowledgeArticle node. ReferenceArticle adds a
REFERENCES_ARTICLE edge and rejects duplicates. RecordResolution creates a Resolution
node and its RESOLVED_BY edge. DeleteArticle removes an article and its incoming
edges, but it must be rejected while REFERENCES_ARTICLE edges still point to the
article unless cascade is true. Every new edge requires existing endpoints of the
expected types. Any attempt to modify a database-derived node property must be
rejected.

Put the shared mutation models in Services/Graph/MutationModels.cs. MutationStatus
should have Rejected, PreviewOnly, and Applied values. MutationPreview should contain
Summary, AffectedFiles, and Warnings. MutationResult should contain Status, Preview,
and Errors, with factory helpers named Rejected, PreviewOnly, and Applied.

Make Services/Graph/GraphMutationService.cs the only component allowed to write graph
files. Protect the write path with SemaphoreSlim so concurrent mutations cannot
interleave. Keep a ReadOnlyNodeTypes set containing Ticket, TicketDetail, Requester,
Status, and Day, and use it to reject forbidden targets consistently.

Every public method on GraphMutationService should follow the same preview and confirm
flow. Once confirmed, work from an in-memory GraphDocument, atomically write graph.json
and manifest.json through a temporary file and move, reload GraphStore, and append one
line to audit.log. Include UpdateNodeContent(nodeId, propertyName, value, confirmed),
which updates one Data property on an existing editable node, or updates its label
when propertyName is "label". This method must never create or delete a node, alter an
edge, or modify a read-only node.

Although the service supports the full mutation domain, expose exactly one write tool
to the AI model. Define IGraphWriteTools and GraphWriteTools in
Services/AI/GraphTools, with UpdateNodeContent(nodeId, propertyName, value) as the
only model-visible write capability. It should delegate to GraphMutationService and
may pass confirmed = true only after human approval. Its [Description] must explain
that this is the sole permitted edit, that it cannot create or delete nodes or edges,
and that database-derived nodes remain read-only.
